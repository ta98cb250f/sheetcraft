# Intervention Log Skill

ユーザーが指摘・修正・誘導する必要があった事象をログに追記し、Claude Code が単体で完結できる範囲を広げるための材料を残す。

## いつ使うか

- 「介入ログ」「intervention log」「振り返り」「セッションのまとめ」と言われたとき
- PR 作成直後・セッション末（ユーザーが「コミットして終わり」のような区切りを示したとき）
- ユーザーから明示的に「ログに残して」と言われたとき

軽微な指示変更（言い回し調整、フォーマット微修正など）は記録しない。

## 手順

1. **ログファイルを開いて方針セクションを確認する**
   ```bash
   sed -n '1,30p' .claude/notes/intervention-log.md
   ```
   書式・カテゴリ・対象外条件を毎回読み直す（蓄積で方針が更新されている可能性があるため）

2. **当該セッションで発生した介入を洗い出す**
   会話履歴をスキャンし、以下に該当するものを拾う:
   - ユーザーが「変わってない」「動かない」「違う」と返した箇所
   - ユーザーが手順・段取り・粒度を指示した箇所（CLAUDE.md / スキルで本来 Claude が自発的にやるべきだったもの）
   - 自分の主張と実機動作が食い違って訂正された箇所
   - 質問・説明の曖昧さを指摘された箇所
   - PR / コミット / サンプルデータ等の整理ミスをユーザーに発見されたケース
   - 同じ問題で 2 回以上イテレーションした箇所（1 回目で気づくべきだった内容）

   **過小列挙に注意**: 「実装は最終的に正しくなった」ケースでも、途中の介入回数が多ければ全て記録対象。
   1 セッションで 10 件以上拾えるのが通常と想定する。

3. **カテゴリを判定する**
   - `指示違反` … CLAUDE.md / スキル / メモリで定義済みのルールを守らなかった
   - `バグ` … 実装ミスで動かない・副作用
   - `仕様理解` … API / フレームワーク / データモデルの前提を誤って実装
   - `環境` … OS / 依存設定の前提ミス
   - `コミュニケーション` … 質問の曖昧さ・確認過多/不足・主張と検証の乖離
   - `プロセス` … コミット粒度・PR 段取り・検証段取り・自発性

   複数該当する場合は主要なものを 1〜2 個に絞る。略称は使わない（「コミュニケーション」を「コミュ」と書かない）。

4. **1 件 = 1 行で追記する**
   ```
   - [カテゴリ] 状況の要点 → 防止策
   ```
   詳細は PR / コミット / 該当ファイルから辿れるので書かない。100 件規模で運用することを意識する。

5. **新しいセッションは最上部の「ログ」見出しの直下に追記する**
   既存セッションのブロックは触らない（同日の追記は同じブロックに足してよい）。
   セッションヘッダは `### YYYY-MM-DD — <branch or PR>（<短い要約>）` の形式。
   ブロック内をカテゴリ別に小見出し (`#### 指示違反・プロセス` 等) で分けても良いが、件数が少なければフラットなリストで構わない。

6. **コミット**
   追記の commit はサブジェクトを `chore: 介入ログを更新 (<日付>)` のように短くする。本文は不要。

## アンチパターン

- ❌ 介入が無かったことにする / 過小列挙する（最も避けるべき）
- ❌ 1 件を複数行に渡って説明する
- ❌ 同じ介入を技術詳細別に複数項目に分割する（根本原因が同じなら 1 件）
- ❌ ルール化済み（CLAUDE.md / スキル反映済み）の再発を新規行として書く（既存行に `→ <反映先>` の注記更新で済ます）
- ❌ ユーザーへの感謝・反省文を本ログに書く（ログは事実記録）
