# Intervention Analysis Skill

介入ログ (`.claude/notes/intervention-log.md`) を分析し、再発パターンを CLAUDE.md / スキル / hook / メモリに昇格させる。

`intervention-log` は「事象を 1 行追記する」スキル。本スキルは「溜まったログを集計し、再発防止策に構造化する」スキル。混同しない。

## いつ使うか

- 介入ログのログ件数が 10-20 件以上溜まったとき
- ユーザーから「分析して」「対策を検討」「振り返り」「同種の介入が多い」と言われたとき
- 月次の傾向集計タイミング

## 手順

### 1. ログ全体を読み込みカテゴリ集計

```bash
cat .claude/notes/intervention-log.md
```

- セッション・PR ごとのブロック (`### YYYY-MM-DD — ...`) を把握
- カテゴリ別件数を数える (指示違反 / バグ / 仕様理解 / 環境 / コミュニケーション / プロセス)

### 2. 再発パターンを抽出

末尾に `(再発)` または `→ <反映先>` が付いている行を集める。同一カテゴリ・同一根本原因のものをグループ化。**複数回出ているパターンが最優先で昇格対象**。

### 3. 頻出だが未ルール化のパターンを特定

`→ <反映先>` が付いていない行のうち、3 件以上同じ系統で出ているものを抽出。これらは昇格候補。

### 4. 昇格先を判断 (マトリクス)

| 介入パターンの性質 | 昇格先 | 例 |
|---|---|---|
| 機械検出可能 (file_path, content の特徴で判定) | `.claude/hooks/pre-tool-use.py` (PreToolUse hook) | メモリ無断作成、空ファイル作成、replace_all 暴発 |
| UI / API 等の対象特定型 | 専用スキル (find-component 型) | コンポーネント特定、AG Grid Community 判定 |
| 着手前にチェックすべき手順 | `.claude/skills/pre-implement-check/` | ブランチ点検、前提ツール検証、untracked 確認 |
| コミット / PR 前にチェックすべき手順 | `.claude/skills/pre-commit-check/` | 動作確認、コミット粒度、差分ノイズ、検証チェックリスト |
| Claude 汎用挙動の指示 (プロジェクト非依存) | メモリ feedback (`~/.claude/projects/.../memory/`) | AskUserQuestion 推奨明示、造語禁止、確認スタイル |
| プロジェクト固有の規則 / データモデル | CLAUDE.md | AG Grid イベント設計、Cell データ構造、実装方針 |

迷ったときの判断順:
1. プロジェクト依存性で分ける (依存→ CLAUDE.md / スキル、非依存→ メモリ)
2. 機械検出可能か (可→ hook、不可→ ドキュメント or スキル)
3. 発火タイミングで分ける (着手前 / 実装中 / コミット前)

### 5. 対策実装の知見 (これまでに得たもの)

新規対策を実装する際は以下に従う:

- **監視 hook は WARN ベース** (exit 0 + stderr) を基本とする。完全ブロック (exit 2) はユーザー承認後の正規パスも潰すので限定的に
- **完全ブロックして良いのは「正規パスでも実行する理由が無い」もの**: 空ファイル作成、短い replace_all の暴発 (これらは常に再考が必要)
- **メモリ書き込み等の「承認後は正規パス」のものは WARN**: hook で警告→ Claude が承認状態を判断して継続
- **コミット粒度を分ける**: ドキュメント / 実装 (hook 等) / 介入ログ更新 / 設計修正 をそれぞれ独立コミットに
- **PR は既存があれば原則更新**: `gh api repos/<owner>/<repo>/pulls/<n> --method PATCH --field title=... --field body=...`
- **`gh pr edit` は Projects classic deprecation で失敗する** → 上記 `gh api` を使う
- **ブランチ分割の判断**: 既存ブランチが同じテーマなら積む、別テーマなら develop から新ブランチ (`git fetch && git checkout -b <name> origin/develop`)
- **新規 hook 実装後は bash 単体テスト**: stdin に JSON を流して exit code と stderr を確認 (実セッション内発火は次セッションで観察)

### 6. 既存行への注記更新

昇格させたパターンの既存ログ行に `→ <反映先>` を追記する。

```
# Before
- [指示違反] メモリ ... → メモリ書込みは確認を挟まなければ実行しない（再発）

# After
- [指示違反] メモリ ... → メモリ書込みは確認を挟まなければ実行しない（再発） → .claude/hooks/pre-tool-use.py (WARN)
```

Edit ツールで old_string は unique な末尾文字列を指定する。複数行への注記は Edit を順次実行する (同一ファイル並列 Edit は避ける)。

注記する行を選ぶ目安:
- 反映先が機械検出 hook なら最優先で注記 (将来の参照価値が高い)
- 反映先がスキル / CLAUDE.md なら主要な行 (3-5 件) に絞ってもよい
- すべての関連行に注記すると差分肥大化するので、対策あたり 2-3 件で十分

### 7. ユーザーへの提示と合意

昇格案は **必ずユーザーに提示して合意を取る** (CLAUDE.md / メモリ / hook の改変は影響範囲が広い)。

提示形式:
- 不足項目を 5-7 件に絞って表形式で
- 推奨対策を 1 つ最初に提示 (理由 1 行付き、`feedback_ask_user_recommended.md` 準拠)
- 着手前に AskUserQuestion で合意確認

### 8. セッション末の総合フロー

```
1. /intervention-log でセッション分の介入を追記
2. (10 件以上溜まれば) /intervention-analysis で集計
3. 昇格対象を特定 → ユーザーに対策案を提示し合意
4. CLAUDE.md / スキル / hook / メモリ を順次更新
5. 既存ログ行に → 反映先 注記を追加
6. 粒度を分けてコミット (/pre-commit-check で点検後)
7. PR を更新 (既存) または作成 (新規、/pr-metadata)
```

## アンチパターン

- ❌ 介入ログを読まずに「直近の記憶」だけで分析 → 過小列挙、再発パターン見落とし
- ❌ 1 セッションで複数対策を一度に走らせる → 着手宣言を踏み倒し、コミット粒度過大、レビュー困難
- ❌ ユーザー合意なしに昇格先を勝手に決めて実装 → メモリ無断作成と同根の指示違反
- ❌ 機械検出可能なものをドキュメントに書くだけで済ます → 強制度が低く再発する
- ❌ 監視 hook で完全ブロック (exit 2) → ユーザー承認後の正規パスを潰す
- ❌ 既存ログ行への注記を全件やる → 差分が肥大化してレビュー困難
- ❌ 介入ログ追記 (`/intervention-log`) と分析 (`/intervention-analysis`) を混同して 1 スキルで両方やる → 発火タイミングと職責が違う
